# 历史 14 条文本主分类评估结果解读

本文件用于解释 `batch_text_eval_20260721_171912` 这次历史文本主分类评估结果。它不替代原始结果文件，而是记录本批次做了什么、后来发现了什么问题，以及为什么不能再把该批次作为干净的质量结论。

> 重要修正：本批次运行时，14 条模型可见样本中包含“运营备注”或同类说明，其中部分文字直接提示了应归入的主分类，形成了标签泄漏。因此，本批次 100.00% Accuracy 和 100.00% Macro-F1 只能证明调用、标签合并和指标计算链路能够运行，不能证明模型在无提示样本上的分类质量。

## 1. 本次评估回答什么问题

本次评估要回答的问题是：

> 历史14条样本如何完成 DeepSeek 调用、人工标签对齐、成本延迟记录和分类指标计算？

这不是通用模型能力评测，也不是线上 A/B 实验。它是项目当前阶段的受控小样本评估，用来证明系统已经具备：

- 构造文本评估样本；
- 维护人工标准答案；
- 调用真实文本模型；
- 记录成本和延迟；
- 计算文本主分类 Accuracy、Macro-F1 和分类级 Precision、Recall、F1；
- 复盘结果边界。

## 2. 样本设计

本次评估样本共有 14 条：

- 8 条基础样本：覆盖新闻资讯、财经商业、广告营销、科技数码、体育健康、娱乐休闲、生活日常、知识科普。
- 6 条混合主题难例：覆盖财经 + 科技、广告 + 科技测评、新闻 + 娱乐、知识科普 + 营销、生活方式 + 商业转化、体育健康 + 新闻事件。

样本采用人工改写方式生成，参考短视频/图文平台常见内容形态，例如标题、口播稿、字幕片段、图文说明和评论区信息。后来复查发现，当时模型可见输入还包含用于解释分类边界的运营备注，且部分备注直接出现主分类答案，造成标签泄漏。

当前 `evaluation/text_topic_small_set/` 已删除这类提示，并扩展到18条样本；其中新增4条长难例，每条约850—950个中文字符。当前18条样本尚未重新调用 DeepSeek，因此本历史批次不代表清理后样本的模型结果。

## 4. 结果为什么有价值

这次结果的价值只在工程链路，不在“100%”这个质量数字：

1. 系统能把模型预测结果和人工标准答案对齐，而不是只展示模型生成内容。
2. 系统能把准确率、成本、延迟放在同一个批次里解释，体现 AI 产经项目关心的模型效果和使用成本。
3. 评估器现在可以输出 Accuracy、Macro-F1 和分类级指标，但历史预测受标签泄漏影响，不能据此判断分类边界能力。
4. 评估过程保留了 `model_calls.jsonl`，可以回查每条样本的模型、供应商、成本、延迟和状态。

## 5. 为什么不能夸大

这次 100.00% 不能被写成可靠模型质量结论，原因有五个：

1. 模型可见样本包含直接或间接提示主分类的文字，存在标签泄漏。
2. 样本量只有14条，远小于真实内容平台每天可能处理的内容规模。
3. 样本是人工改写样本，不是从真实线上流量中抽样得到。
4. 评估只覆盖 `topic` 主分类，不覆盖摘要、关键词、副分类、图片或视频结果。
5. 当前分类结果由单一 DeepSeek 文本分析模型生成，没有和其他供应商做横向对照。

更稳妥的表述是：

> 历史14条样本完成了 DeepSeek 调用、人工标签合并、成本延迟记录和指标生成，但复查发现模型输入存在标签泄漏，因此该批次只能作为工程链路证据，不能作为干净的模型质量证据。

## 6. 成本与延迟解读

本批次总成本为 0.015414 元，说明小样本文本评估的 API 成本可控。平均每条样本成本约为 0.001101 元，适合在开发阶段做小规模迭代验证。

延迟方面，平均模型调用延迟为 3314.07 ms，P95 模型延迟为 6432 ms。最慢样本是 `file_0001`，对应 `01_news_city_transport.txt`。这说明当前文本评估的主要等待时间来自真实模型调用，而不是本地评估器逻辑。

如果后续要把它用于更大批量评估，应关注：

- 是否需要并发调用；
- 是否需要设置重试和超时；
- 是否需要按预算限制自动截断评估任务；
- 是否需要区分开发评估和生产评估。

## 7. 工程复盘时应该怎么说明

可以这样讲：

> 历史14条评估让我验证了真实调用、人工标签对齐、成本延迟记录和指标生成，但后续复查发现输入中混入了分类提示。我没有继续使用这个100%作为质量证据，而是删除标签泄漏、补充4条长难例，并增加 Macro-F1 和分类级指标。清理后的18条样本需要重新做一次受控真实评估，才能产生新的质量结论。

## 8. 下一步建议

如果继续补强这个功能，建议仍然只围绕文本评估，不立刻扩到新功能：

1. 在用户明确授权后，只对清理后的18条样本进行一次受控 DeepSeek 调用。
2. 生成新的 Accuracy、Macro-F1 和分类级指标报告，并检查长文本和 `other` 分类错例。
3. 在新结果通过复核前，不开启 OCR、ASR、多供应商对照或其他功能。

## 9. 字段说明

| 字段 | 含义与作用 |
|---|---|
| `batch_id` | 一次批处理任务的唯一标识，用于定位本次评估批次。 |
| `file_id` | 单个文本样本在批次中的唯一标识，用于关联结果和模型调用。 |
| `file_name` | 文本样本文件名，用于人工识别样本内容。 |
| `predicted_topic` | DeepSeek 预测出的主分类，用于和人工标准答案比较。 |
| `gold_topic` | 人工标注的正确主分类，是本次评估的基准答案。 |
| `reviewer_note` | 人工评审备注，用于说明样本为什么属于某个主分类。 |
| `accuracy` | 文本主分类准确率，计算方式为预测正确数除以已评估样本数。 |
| `macro_f1` | 各参与评估分类 F1 的简单平均，用于避免总体正确率掩盖小类别问题。 |
| `precision` | 预测为某个分类的样本中实际属于该分类的比例，用于观察误报。 |
| `recall` | 实际属于某个分类的样本中被正确识别的比例，用于观察漏报。 |
| `f1` | 单个分类 Precision 和 Recall 的调和平均，用于综合评价误报与漏报。 |
| `support` | 某分类的人工标准答案样本数，用于判断该分类证据量。 |
| `total_cost_cny` | 批次总成本，单位人民币，用于评估 API 调用成本。 |
| `latency_ms` | 单次模型调用耗时，单位毫秒，用于定位慢调用。 |
| `p95_model_latency_ms` | 模型调用 P95 延迟，单位毫秒，用于观察尾部延迟风险。 |
