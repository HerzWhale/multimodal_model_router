# 暂缓扩展的技术问题记录

本文用于记录当前项目中已经识别、但暂时不适合继续扩展的问题。

它不是失败清单，也不是放弃清单。它的作用是把边界说清楚：哪些问题已经有证据，为什么现在不继续扩大，未来在什么条件下再回来处理。

当前项目原定位仍然是：面向内容平台 AI 团队技术负责人的多模态批处理与模型路由 MVP。文本分类、图片 OCR、成本延迟记录、模型调用追踪和后端取舍判断，都是在逐步支撑这个总定位；不能把项目收缩成“只做文本分类”，也不能为了显得完整同时铺开 OCR、ASR、视觉理解、视频抽帧、前端和多供应商接入。

## 一、判断原则

后续遇到新功能时，先按下面四个问题判断是否应该暂缓：

1. 当前是否已有真实输入、真实输出和可复现实验；
2. 当前是否能解释成本、延迟、质量和失败边界；
3. 新功能是否会依赖一个还没有过闸门的上游能力；
4. 新功能是否只是让项目“看起来更完整”，但不能提高真实可信度。

如果答案显示风险过高，就先进入本文记录，不直接开发。

## 三、小字号 OCR 问题的技术归因

这一节专门记录“为什么 PaddleOCR 和 RapidOCR 在小字号上迟迟达不到应有水准”。

当前证据：

- PaddleOCR 关键帧批次：完整段落召回率 78.05%，字符错误率 11.01%，P95 延迟 28261ms；
- RapidOCR 关键帧批次：完整段落召回率 82.93%，字符错误率 10.64%，P95 延迟 4294ms；
- `img_9.jpg` 是共同弱样本：PaddleOCR 完整段落召回率 47.62%，RapidOCR 完整段落召回率 54.76%；
- `img_9.jpg` 的错误集中在小字号结构图文字，例如模块名、缓冲区容量、TLB 页表项等技术参数。

主要原因如下。

第一，小字号不是“文字小”这么简单，而是像素信息不足。OCR 模型看到的是像素，不是人脑理解后的文字。当文字高度只有很少像素时，笔画、空隙、下划线、数字边界会糊在一起。变量名、英文缩写、数字单位和下划线结构尤其容易被误识别或漏识别。

第二，视频关键帧天然比原图更难。关键帧可能经历过平台压缩、分辨率降低、码率损失、边缘模糊、二次截图和二次压缩。大字还能保留轮廓，小字可能已经损失关键笔画。简单放大只能放大模糊像素，不能恢复原始信息。

第三，当前样本不是普通文档 OCR，而是技术结构图 / 参数表 / 小字号信息图。它同时包含多栏布局、框线、英文缩写、下划线变量、数字容量和标签值对应关系。通用 OCR 更擅长清晰文档、票据、普通截图和横排文字；面对复杂结构图时，检测文字框和保留上下文关系都会变难。

第四，OCR 通常分为检测和识别两步。小字号会在检测阶段漏掉文字框，也会在识别阶段把框内字符认错。当前错误表现符合这个规律：有些地方数值被识别到但标签缺失，有些地方标签被识别到但容量或 Entry 数值缺失。

第五，当前完整段落召回率指标本身比较严格，但这符合业务目标。生产场景不是只要求“看起来像”，而是要求关键业务文字完整保留下来。例如标签和值的对应关系如果丢失，下游文本分析就会基于残缺证据生成结果。

第六，RapidOCR 更快但没有解决质量边界。它把关键帧批次 P95 延迟从 PaddleOCR 的 28261ms 降到 4294ms，说明本地推理效率更好；但 `img_9.jpg` 的小字号结构图识别仍未通过，说明问题不只是 PaddleOCR 的单点实现，而是本地通用 OCR 在该类输入上的能力边界。

因此，当前结论是：不应继续无约束地堆更多本地 OCR 候选。更合理的处理方式是保留 PaddleOCR 作为本地基线，把 RapidOCR作为已评估未通过候选记录下来；如果继续追求生产可用 OCR，需要在用户授权后做服务化 OCR 小样本评估。

## 四、当前可以对外或面试中诚实表达的说法

可以说：

> 我没有把 OCR 部分简单写成“已完成”。我先接入了本地 PaddleOCR，再用真实关键帧图片和人工基准做分段评估，发现小字号结构图是主要弱点；随后评估 RapidOCR 作为本地候选，速度改善明显，但质量和 P95 延迟仍未过闸门。因此当前项目把 OCR 明确收敛为“有真实证据的本地基线 + 候选评估 + 后端取舍判断”，而不是强行宣称图片理解已经生产可用。

不应该说：

> 项目已经完成完整图片理解。

也不应该说：

> RapidOCR 已经替代 PaddleOCR。

## 五、相关字段说明

| 字段 | 含义与作用 |
|---|---|
| `ocr_text` | OCR 提取的图片文字证据，用于后续文本分析和人工质量评估 |
| `exact_segment_recall` | 完整识别的必选业务文字块占比，用来衡量 OCR 是否漏掉关键内容 |
| `character_error_rate` | 字符编辑距离除以人工正确字符总数，用来衡量 OCR 错字、漏字和多字程度 |
| `ocr_latency_ms` | 单张图片 OCR 耗时，用来判断单图处理是否满足延迟目标 |
| `ocr_p95_latency_ms` | OCR 耗时的 95 分位，用来判断慢调用是否影响批次性能 |
| `gate_status` | 候选后端是否通过当前质量和延迟闸门，用于决定是否接入主流程 |
| `candidate_evaluations` | 候选 OCR 后端的已评估结果摘要，用来避免重复推荐已实测未通过的方案 |
| `recommended_next_backend_id` | 下一步建议评估的后端标识，只表示测试建议，不表示已经接入 |
| `ocr_external_api_cost_cny` | OCR 外部 API 成本；本地 OCR 为 0 元，但不包含本机算力、电力和维护成本 |
